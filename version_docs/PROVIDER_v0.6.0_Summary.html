Phase B + Extension — Storage & Sourcing

Wholesaler Storage Cap & Visible BRA→USA Switching

🏭

Wholesaler Storage Capacity

Before: my_share = total_supply / n_wholesalers — no upper bound, infinite storage. Now: my_demand = min(normal_capacity / n_wholesalers, storage_capacity). Default cap: 20 000 t. Field storage_utilization (stock ÷ capacity) is tracked and written to the database every tick.

📊

Push → Pull Sourcing

Before: wholesaler demand shrank with BRA supply — if BRA falls 30%, demand falls 30%, USA never needed. Now: demand target is fixed at sum(base_yield), independent of disruption. USA offers 1.5× its base yield (usa_surplus_factor) but prices at cost — stays expensive at baseline, gets called when BRA can't fill the gap.

Old (Push Model)
  • Demand = total BRA supply ÷ n_wholesalers
  • Demand shrinks when BRA drops
  • USA never needed to fill a gap
  • BRA→USA switch invisible on plot
  • USA always priced identically
→
New (Pull Model)
  • Demand = sum(base_yield) ÷ n_wholesalers
  • Demand stays fixed under BRA shock
  • Gap forces wholesaler to pull from USA
  • BRA drop / USA rise visible in plot
  • usa_surplus_factor = 1.5 in scenario.py
# agents/trader.py — _step_wholesaler() — core change
# Demand is now anchored to base_yield sum, not disrupted supply

normal_capacity = (
sum(f.base_yield for f in active_bra) +
sum(f.base_yield for f in active_usa)
)
my_demand = min(normal_capacity / n_wholesalers, self.storage_capacity)

# agents/farmer.py — _step_usa() — surplus capacity
# Offer more volume than base, but price at base cost → stays expensive at baseline
self.quantity_available = self.base_yield * self.scenario.usa_surplus_factor
self.unit_price = (self.fixed_costs / self.base_yield) * (1.0 + self.margin)

# scenario.py — two new parameters
wholesaler_storage_capacity: float = 20_000.0 # tonnes / step
usa_surplus_factor: float = 1.5 # USA offers 150% of base_yield

Option A — Tick Writer

Tick-Based Postgres Logging — Not End-of-Simulation Batch

Why this matters

palaestrAI needs to query data mid-run — pause at step t, inspect state, alter parameters, resume. Batch import (write-all-at-end) makes this impossible. The new tick writer commits one row per agent per step to Postgres inside run_stepwise(), after every _do_step(t). Data is queryable from step 0 onward.

from db_config import PostgresDBConfig
from tick_writer import TickWriter

id_scenario = getattr(self.scenario, "id", 0)
tick_writer = TickWriter.from_config(
PostgresDBConfig(),
reset=(id_scenario == 0) # ← drop tables only once per full run
)

for t in range(self.scenario.period_num):
self._do_step(t)
tick_writer.write_tick(
self, id_scenario=id_scenario, id_run=0, t=t
)
yield { ... }
🐛

Multi-Scenario Bug — Fixed

Melodie creates a new model object per scenario, so a new TickWriter was created each time. Without the reset flag, every scenario wiped the previous scenario's data. Result: only the last scenario's 52 rows survived instead of 156 (3 × 52). Fix: reset=(id_scenario == 0) — tables are dropped exactly once per full run.
