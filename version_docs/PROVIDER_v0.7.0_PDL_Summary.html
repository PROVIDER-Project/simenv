01 — What is PDL

Provider Domain Language

Definition

PDL (Provider Domain Language) is a YAML-based domain-specific language developed by Implisense as part of the PROVIDER project. It provides a standardised, human-readable format for describing supply chain disruption scenarios — independent of any specific simulation tool.

Role in the System

PDL is an input file, not an output. It is written by domain experts or generated from knowledge graph data, and fed into a simulation like simenv. Our task was to build the translator so simenv can actually read and consume it.

📄

PDL vs. the old approach

Before PDL integration, shock parameters were hardcoded manually in SimulatorScenarios.csv — three rows written by hand. There was a shock_loader.py stub for KG-format shocks but it was never wired in.

PDL replaces the manual CSV editing workflow. A single YAML file from the reference repository now fully drives the simulation parameters via --pdl. The PDL loader is the first real implementation of the scenario ingestion interface.

🗂️

Standardised Format

PDL schema version 1.1. All files follow the same JSON Schema (pdl-schema.json). Any compliant scenario file — not just s1-soja — can be fed to the loader without code changes.

🔗

Knowledge Graph Bridge

PDL serves as the bridge between the CoyPu Knowledge Graph and simulation tools. KG events and impact magnitudes are expressed in PDL, then translated into numeric scenario parameters.

⚙️

Simulation-Agnostic

PDL does not describe how a simulation works internally. It only describes what happened in the real world and by how much. The translator layer (pdl_loader.py) handles the conversion to simenv's internal parameters.

02 — PDL File Contents

What's Inside a PDL File — s1-soja.pdl.yaml

PDL Section What It Contains Count (s1-soja) Used in simenv
scenario ID, name, sector, criticality, description 1 Label only — scenario name printed to console
entities All actors in the chain: farms, ports, mills, consumers, commodities. Each has id, type, location, vulnerability. 20 Not used — entity metadata not consumed. IDs are only used as lookup keys in the mapping table.
events Disruption events with trigger target + impact magnitude (supply %, price %, duration). The core shock data. 18 Primary source — 6 of 18 events map to simenv params. The other 12 are silently skipped.
supply_chains Named chain routes with stage arrays (from→to) and dependency links between entities. 5 Not used — simenv's chain topology is hardcoded in agent classes. PDL topology is separate concern.
substitutions Resilience mechanisms: supplier switches, product substitutions, route alternatives. Includes coverage %, cost delta, ramp-up time. 6 Not used — substitution logic is a separate model feature (out of current scope).
cascades Named crisis timelines linking events with day offsets (at: 14d, at: 42d…). Three cascade scenarios: soy crisis, energy-food, compound. 3 Not used — timing extraction is the planned next step. Currently only impact magnitudes are used.
Important Distinction

The loader reads the flat events list only — not the cascades timeline. This means event timing (at: 14d, at: 42d) is ignored in the current version. All mapped impacts are applied as static shocks for the full simulation run.

Template CSV — Anti-Contamination

SimulatorScenarios_template.csv is the source of truth and is never modified. Before every run, main.py copies it to the working CSV. This prevents a previous --pdl run from permanently corrupting the baseline — a silent bug that existed before this fix.

🎯

s0 = Always Baseline

PDL overrides are applied only to CSV rows with id > 0. Row 0 (s0) is always kept at capacity=1.0 — the true unshocked baseline. This makes s1/s2 directly comparable to s0 in every PDL run without manual intervention.

04 — Current Implementation

What pdl_loader.py Does — and How

Translation Logic

The loader scans the PDL events list. For each event it reads trigger.target (which entity) and impact.supply / impact.price (the percentage string). It looks up the (entity_id, field) pair in a mapping table to get the simenv parameter name, then converts the percentage to a float multiplier.

Conversion Math

"-40%" → 1.0 + (−40 / 100) = 0.60
"-20%" → 1.0 + (−20 / 100) = 0.80
"+200%" → 1.0 + (200 / 100) = 3.00
"+80%" → 1.0 + (80 / 100) = 1.80
# pdl_loader.py — _PDL_MAPPING
# Key: (PDL entity id, impact field)
# Value: scenario.py parameter name

_PDL_MAPPING = {
  ("brazil_farms", "supply"): "farm_capacity_bra",
  ("santos_port", "supply"): "port_capacity_sa",
  ("paranagua_port", "supply"): "port_capacity_sa",
  ("gas_supply", "price"): "energy_price_factor",
  ("fertilizer_supply", "price"): "fertilizer_price_factor",
  ("eu_oil_mills", "supply"): "oil_mill_capacity",
}

# Aggregation when multiple events hit the same param:
# capacity → min() (worst-case degradation)
# price → max() (worst-case spike)

05 — Scope Boundaries

What Is Out of Current Scope

Skipped from PDL — Impact Magnitudes Only

Event duration field e.g. duration: 90d. Read by YAML parser but never extracted — current implementation treats all shocks as permanent.
Cascade timeline offsets at: 14d, at: 42d entries in each cascade define when events trigger. Not consumed — planned as next step.
12 of 18 event impacts Events targeting feed_mills, poultry_farms, consumers, etc. have no mapping to simenv params — skipped silently.

Separate Concern — Different Feature

PDL substitutions section Describes resilience mechanisms (BRA→ARG supplier switch, protein substitution). Requires a dedicated substitution model in simenv — separate implementation task.
PDL supply_chains topology Defines the full chain graph (routes, ports, dependencies). SimEnv's agent topology is hardcoded in agent classes — wiring PDL topology would restructure the model.
PDL entities metadata Vulnerability scores, location, sector — structural information about each actor. Not a simulation parameter today; could feed a future risk-weighting layer.
06 — Next Step

Planned: Timing Extraction from PDL Cascades

The Gap

PDL cascades define exactly when each event triggers — e.g. brazil_drought at day 0, feed_price_spike at day 28, livestock_pressure at day 42. This temporal structure exists in the file but is completely ignored by the current loader. All shocks are applied statically for the full simulation run, regardless of when they happened in reality.

📅

How It Would Work

Read the cascades[].timeline[].at field for each event. Convert the day offset to a simulation week (days ÷ 7). Use this value to set shock_onset_step for the corresponding scenario row.

The ramp duration could be derived from the PDL event's own duration field, also converted to weeks. This would make the simenv timing parameters fully PDL-driven.

# What the cascade section provides:
# cascades[0].timeline:
at: 0d → brazil_drought # onset week 0
at: 14d → soy_export_reduction # onset week 2
at: 28d → feed_price_spike # onset week 4
at: 42d → livestock_pressure # onset week 6

# What we currently pass to SimulatorScenarios.csv:
shock_onset_step = 13 # hardcoded ← should come from PDL
shock_ramp_steps = 13 # hardcoded ← could come from duration

# Planned output of timing extractor:
shock_onset_step = round(0 / 7) # = 0
shock_ramp_steps = round(90 / 7) # = 13
Unit Mismatch

PDL expresses time in days. SimEnv runs in weeks. Any timing extraction must divide PDL day values by 7 and round to the nearest integer step. This is a known, documented mismatch — not a blocker for the current implementation.
