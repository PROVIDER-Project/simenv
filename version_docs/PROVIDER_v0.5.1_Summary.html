01 What We Implemented

Three deliverables — storage, visualization, and a PostgreSQL adapter.

New

SQLite Persistence

After every simulation run, all Result_Simulator_*.csv files are merged into a single provider-simenv.sqlite database via csv_to_sqlite() in main.py. Each CSV becomes one table. The database is rebuilt from scratch on every run.

New

Simulation Plots

visualize_sql.py reads from the SQLite database and produces two publication-ready PNGs: a price development chart (soja + feed across all drought scenarios) and a sourcing volume flow chart (BRA vs USA split, one panel per scenario).

New

PostgreSQL Adapter

db_config.py provides a PostgresDBConfig dataclass holding connection parameters. csv_to_postgres() in main.py mirrors the same CSV data to a Postgres database, designed for future palaestrAI connectivity.

Enhanced

DataCollector Fix

Two bugs in Melodie's DataCollector were patched: the status property now always returns True (fixing a silent data-drop in the normal Simulator.run() path), and bra_volume / usa_volume were registered for wholesalers so sourcing splits are captured per step.

02 SQLite — The Problem & The Fix

Two silent bugs in Melodie — both discovered, both circumvented.

Bug 1 — DataCollector.status

Melodie's DataCollector.collect() checks self.status, which by default calls isinstance(scenario.manager, Simulator). In the normal Simulator.run() path, scenario.manager is never set — it remains None. The isinstance check returns False, and every collect() call is silently skipped. Result: all output tables are empty. Fix: override status to always return True.

Bug 2 — SQLAlchemy 2.0 Missing Commit

Melodie's built-in data_output_type="sqlite" routes output through MelodieInfra.DatabaseConnector.write_table(), which opens a connection via with engine.connect() as conn: and calls conn.execute(sql, data). In SQLAlchemy 2.0, a transaction opened with engine.connect() requires an explicit conn.commit() — without it, the transaction rolls back silently on exit. Tables are created (DDL auto-commits in SQLite) but all INSERT rows vanish.

Melodie Built-in SQLite Path
  • Set data_output_type="sqlite"
  • Uses SQLAlchemy 2.0 internally
  • Missing conn.commit() in library
  • All INSERT rows silently rolled back
  • Tables exist but are empty
→
Our Workaround
  • Melodie writes CSVs (default, proven path)
  • Post-process with csv_to_sqlite()
  • Uses sqlite3 + pandas directly
  • Explicit conn.commit() — no SQLAlchemy
  • All rows persisted correctly
Why not patch the library?

Patching MelodieInfra directly would be silently overwritten on the next pip upgrade, would only exist on one machine, and would not be tracked in git. The csv_to_sqlite() function in main.py is fully version-controlled, portable, and survives any library update.

03 PostgreSQL Adapter

Ready for palaestrAI — graceful fallback when no instance is running.

COMPONENT 01
db_config.py — a PostgresDBConfig dataclass holding host, port, dbname, user, and password. Defaults point to a local instance. Override at runtime with environment variables for production. Password is always masked in __repr__ to prevent accidental logging.
COMPONENT 02
csv_to_postgres() in main.py — mirrors all Result_Simulator_*.csv files to PostgreSQL using engine.begin() (SQLAlchemy's auto-committing context manager). Uses psycopg2 as the driver and pandas.to_sql() in replace mode for idempotent reruns.
COMPONENT 03
Graceful fallback — before writing any data, csv_to_postgres() tests the connection with a SELECT 1. If Postgres is unreachable, the exception is caught, a clear warning is printed, and main.py continues normally. SQLite output is never affected.
USAGE — FUTURE
To activate: start a PostgreSQL instance (local Docker or palaestrAI server), set credentials in PostgresDBConfig or via environment variables, and run main.py. Data flows automatically. Grafana can then be pointed at the Postgres database for live dashboards.

04 Simulation Output

Price propagation and origin switching — visualized across three scenarios.

Price Development — Wholesaler & Feed Trader Level

The baseline scenario (blue) holds flat throughout — no drought, no price shock, soja price stays around 525 EUR/t and feed around 1,280 EUR/t. The mild drought (orange) begins showing price pressure around step 13 and stabilizes at a new equilibrium by step 25 — soja near 615 EUR/t, feed near 1,465 EUR/t. The severe drought (red) drives a sharper ramp, crossing the mild scenario's peak and settling at 720 EUR/t soja and 1,820 EUR/t feed. Prices plateau once the shock stabilizes — there is no recovery within the 52-step window, reflecting the real-world lag in supply chain adaptation.

Sourcing Volume Flow — BRA vs USA Split

The baseline panel (top) shows full BRA dominance throughout — around 1,000 t from Brazil and 775 t from USA each week, stable and flat. This is the expected equilibrium when BRA prices are lower. Under mild drought (middle), BRA volume drops from ~1,050 t to ~870 t by step 50 as Brazilian prices rise. USA volume rises to compensate — the wholesaler greedily switches sourcing without any hardcoded logic. The severe drought panel (bottom) shows the same dynamic accelerated: BRA contribution falls to ~775 t while USA rises. Total supply contracts slightly due to BRA capacity constraints, visible as the slight downward slope in combined volume. This emergent sourcing shift is the core behavioral output of v0.5.0's greedy algorithm, now captured and persisted in the database for the first time.
